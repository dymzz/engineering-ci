# Release Readiness

本文定义 Engineering CI 正式版本发布前的交付验收要求。

Release Readiness 负责判断候选版本是否具备对外交付条件，不负责执行 CI/CD、发布编排、Tag 创建或 Release 发布。

具体执行流程、检查策略及证据生成由相应实现组件负责。

## 1. Applicability

正式 Release 准备阶段应评估本文件中的适用条件。

- 普通开发、PR 检查和日常测试不触发完整 Release Readiness。
- 仅验证 Release 流程而不发布版本时，按验证任务实际范围检查。
- 正式发布前必须完成适用项目的验收。
- 不适用的检查可以标记为 `N/A`，并说明原因。
- 未验证的条件不得视为通过。

验收结果不代替用户的正式发布授权。

## 2. Release Candidate

在评估前确定候选版本的实际交付身份：

- 目标版本及版本标识。
- 对应的 Git Commit SHA。
- 实际交付的包、模块及公共接口。
- 本次公开行为的变更范围。
- 适用的运行环境与依赖约束。

版本元数据、构建产物和交付目标必须能够对应到确定的源码版本。

不使用其他提交、历史版本或无关执行结果代替当前候选版本的验证证据。

发布前的评估范围是 **preparation**：确认候选身份、消费与失败契约及既有正式发布机制。
此时尚不存在的新版本 Tag、Release URL 与最终 Manifest 标为待发布后核验，不能伪造。
发布后以 **publication** 范围补核实际 Tag/SHA、Release 和 Manifest；只有读回一致才确认交付完成。
这两个范围是验收时序，不是新的执行状态机，也不要求预先创建 Tag 来满足准备评估。

## 3. Public Component Acceptance

公共组件交付采用以下八项验收条件。

### C1. Independent Consumption

消费者能够通过正式提供的安装或引用方式使用组件。

验收要求：

- 不依赖提供方的私有开发目录或临时构建状态。
- 所需运行环境、依赖和外部服务已明确说明。
- 可以固定所消费的组件版本。
- 公开的消费方式能够独立验证。

### C2. Public Contract

实际支持的公共接口具有明确的契约。

验收要求：

- 公开入口与内部实现有清楚的边界。
- 输入参数、输出类型、错误语义和副作用已有说明。
- 公共接口与实际代码一致。
- 已废弃或发生破坏性变化的接口得到明确标识。

不将所有可调用的内部方法默认视为公共 API。

### C3. Documentation

消费者能够通过正式文档理解和使用组件。

验收要求：

- 存在可发现的文档入口。
- 包含安装、快速开始和接口参考。
- 包含必要的集成、配置及故障处理说明。
- 文档与当前发布版本对应。
- 不存在影响正常集成的失效链接或过时接口示例。

公共使用说明不应要求消费者先阅读内部实现源码。

### C4. Reproducible Examples

公开接口具有可复现的使用示例。

验收要求：

- 示例使用正式公开的接口。
- 必要的配置、依赖与执行条件已说明。
- 示例能够在声明的环境中运行。
- 示例结果与文档描述一致。

示例不要求覆盖全部内部实现路径。

### C5. Failure Semantics

消费者能够正确区分执行结果。

验收要求：

- 成功、失败、跳过、取消和不可用等适用状态具有明确含义。
- 输出文件或报告生成成功不等于原始执行成功。
- 必需执行失败或缺少结果时，不得报告成功。
- 错误与异常能够通过公开接口被识别。

保留现有接口声明的错误与状态语义。

### C6. Versioned Delivery

发布内容能够绑定到确定版本。

验收要求：

- 版本标识与实际交付内容一致。
- 公共 API、文档和示例对应同一交付版本。
- 消费者能够使用固定版本而非依赖可变开发分支。
- 正式发布结果可以追溯到对应源码提交。

具体的 Tag、Artifact 和 Release 生成机制由发布实现负责。

### C7. Consumer Verification

公共接口具有实际消费验证依据。

验收要求：

- 至少存在一条经过验证的独立消费路径。
- 相关验证通过正式公开接口执行。
- 消费者能够正确获取执行结果及适用的交付产物。
- 影响公共接口的变更具有相应兼容性验证。

对于未改变的接口，可以复用仍然有效的既有验证依据；若依赖、执行环境或相关契约发生变化，应重新判断证据是否适用。

不得把提供方的内部单元测试直接等同于独立消费者验证。

### C8. Compatibility & Evolution

版本升级的影响能够被消费者理解和处理。

验收要求：

- 识别本次变更是否影响公共接口或既有消费者。
- 明确破坏性变更、废弃接口和必要的迁移操作。
- 升级说明反映实际发布行为。
- 已知的不兼容或未验证范围得到披露。

不要求所有版本保持完全向后兼容，但必须明确实际兼容范围。

## 4. Verification Evidence

验收依据应来自现有代码、文档、测试、执行报告及实际消费结果。

| 条件 | 适用范围 | 必需证据与限制 |
| --- | --- | --- |
| C1 | 本次声明支持的安装、模块或 Workflow 消费方式 | 独立环境的固定版本/提交和安装、调用结果；仅 checkout 内导入不充分 |
| C2 | 本次公开支持的接口 | 实际签名/输入、输出与错误契约核对；内部、兼容、实验接口明确分类，不升级为隐含保证 |
| C3 | 声明支持的消费路径 | README 导航、安装/集成/故障说明及有效链接；文档存在本身不构成集成通过 |
| C4 | 交付所依赖的代表性公开示例 | 对应版本、环境、命令和实际结果；未执行平台或分支写 NOT VERIFIED |
| C5 | 每条适用的结果交付和严格门禁路径 | 真实失败与退出/异常、报告或下载结果分离的证据；Mock 与真实执行分开记录 |
| C6 | 所有正式版本交付 | preparation 核验四处元数据、候选 SHA 和不可变交付路径；publication 读回实际 Tag/Release/Manifest 关联。准备 PASS 不声称正式发布已经成功 |
| C7 | 至少一条独立消费者路径及受变更影响的接口 | 固定引用、公开入口与实际消费结果；历史证据必须说明仍适用，远端未运行不能写成远端通过 |
| C8 | 本次公开行为和依赖变化 | 升级/迁移说明、默认调用兼容性和已知限制；N/A 必须明确不适用原因 |

每项条件记录以下状态之一：

| Status | Meaning |
|---|---|
| PASS | 验收条件满足，具有对应证据 |
| FAIL | 已确认不满足验收条件 |
| NOT VERIFIED | 证据不足，尚不能确认 |
| N/A | 当前交付不适用，已说明原因 |

证据应尽可能关联具体版本、提交或执行结果。

现有 CI/CD 报告、消费者测试和 Release 证据可以直接复用，无需为了 Readiness 重复执行等效检查。

历史验证仅在其适用范围仍然成立时有效。

## 5. Release Decision

正式发布前汇总 preparation 范围的适用条件；发布后补齐 publication 核验。

**READY**

- 所有适用的必需条件均为 PASS。
- 不适用项目已有合理说明。
- 没有阻断交付的已知问题。

**BLOCKED**

- 存在不满足的必需验收条件。
- 必需条件仍处于 NOT VERIFIED。
- 候选版本、接口或验证证据存在无法确认的冲突。

对于未纳入本次公开交付范围的实验性或内部功能，不应自动扩大验收范围。

Readiness 结论仅代表交付准备状态，不代表已获得发布授权，也不代表发布操作成功。

## 6. Release Execution Boundary

本文件不定义或重复以下实现：

- CI/CD Workflow DAG。
- 测试及质量门禁的具体执行顺序。
- Release Manifest Schema。
- Tag、Draft、Artifact 的创建与恢复流程。
- 发布平台的权限与 API 操作。

这些内容由其实际实现和接口契约维护。

正式发布仍须遵守现有发布机制、权限要求及用户授权。

Readiness 检查不能绕过或降低任何现有发布门禁。

## 7. Assessment Output

准备正式 Release 时，提供简明验收摘要：

- Candidate version
- Commit SHA
- Public interface changes
- C1–C8 acceptance status
- Evidence references
- Known limitations
- Decision: READY / BLOCKED

只有实际完成的验证才能标记为 PASS。

优先使用现有 PR、Release 或任务交付记录保存结果，不要求额外建立独立的状态管理系统。

## 8. Maintenance

当公共接口、依赖方式、交付职责或发布要求发生变化时，更新受影响的验收条件。

本文件定义交付要求，不维护具体工具的操作步骤和实现细节。

技术契约、使用示例和执行机制在各自的权威文档中维护，避免重复定义与版本漂移。
