# Harness 历史设计与阶段交付

本页归档 v0.5.5–v0.6.5 在 engineering-ci 中开发 Harness 时的版本依据、阶段安排与设计审查。
正文的“当前”“本轮”和原代码路径均按对应版本解释，不是分仓后的当前操作指令。
技术契约已经按所属仓库迁移；不得把旧待办重新安排为必需工作，或把计划表当作实际通过证据。
实际执行记录分别见[轨迹验收](trace-validation.md)、[工作流验收](workflow-validation.md)和[分仓验收](repository-split.md)。

## 初始范围与基线

本文保留 pre-0.6.0 的设计范围、架构边界和交付步骤。前期代码随 PR #20 合并；过渡交付分别为 v0.5.5 的 P0 查询/关联与 Rust4PM、v0.5.6 的 P1 遥测/比较、v0.5.7 的 P2 候选与审查依据。v0.6.0 已正式发布；v0.6.1 的首个固化目标为基础 PR 检查的同输入复用。各阶段按下文实施；已完成证据见[轨迹验收](trace-validation.md)。
基线为正式 v0.5.4，提交 `f1d7d31014417468fa7299be27a86f0a57b47521`。
P0-0 至 P0-4 已实现并获得分阶段实测证据，版本元数据在功能 PR 交付前统一准备。
归档存储复用本地宿主 PostgreSQL，由 `VESRYN_DATABASE` 提供连接配置；不保留 SQLite 后端或回退。

## 版本升级依据

v0.6.0 的新增公开能力是：将实际 Agent 操作归档为可回放的证据，
并基于同一份证据提供不依赖 LLM 的离线流程分析。
它使 engineering-ci 从调用既定检查和交付流程，开始具备观察执行历史、
分析流程变体并提出改进候选的能力。安装 OTel、增加数据库或定义新概念本身不构成完成依据。

[SemVer](https://semver.org/) 对 0.y.z 阶段不承诺稳定公开 API。
本项目仍应保持已有检查、下载、恢复和发布契约；用 0.6.0 标识新增的能力域，
而不是借版本变化破坏现有消费者。补丁版本继续用于该能力域内的正确性修复。

v0.6.0 不应声称整个自动优化循环已经实现。最低交付范围为：

1. 一个真实支持的数据来源，来源能力和限制经过实录核对。
2. 保留原始字节的归档、幂等导入、恢复导入与回放。
3. CloudEvents 封装与少量归档元数据；来源完整性可以解释。
4. 复用标准 OTel 数据模型及成熟插桩；支持范围内的数据可以重新生成标准化视图。
5. 同一固定数据集的非 LLM 变体分析；具备适当事件顺序和时间信息的数据可调用 Rust4PM 发现 DFG。
6. 分析结果可追溯到原始事件，并明确未支持、未知或缺失的信息。

跨运行优化效果验证、LLM 辅助建议、Workflow IR 及编译器属于后续阶段，
不能用尚未实施的加分目标替代上述验收。范围已按本方案确定，代码和四处版本元数据在同一个功能 PR 交付。

## 实施顺序与阶段验收

首个实际来源为用户授权的单个桌面 Codex 原生 rollout JSONL（生产者 0.162.0-alpha.2），按固定文件前缀离线导入，不再次执行 Agent。该内部格式与公共 codex exec --json 事件流分开；后者不作为导出现有会话的命令。
已有 OTel 数据保留原生形式；其他运行时的在线插桩按实际需求接入成熟实现，首轮不同时建设多个采集后端。格式核对只采样文件开头和末尾，其余 Codex 输出默认可信；归档和挖掘按职责流式处理实际字节，不把采样当成全量检查。
原始归档与非 LLM 分析是 pre-0.6.0 的设计范围；本轮按用户选择以 v0.5.5 过渡交付；LLM、可观测性后端和候选固化不阻塞本轮交付。

| 顺序 | 实施动作 | 完成证据 |
| --- | --- | --- |
| P0-0 宿主与连接 | 读取 VESRYN_DATABASE；使用 Psycopg 做脱敏配置解析、连接及只读版本/schema/权限核对 | 缺配置、认证/网络/权限错误可区分；确认实际目标和专用 schema，未核对前不执行迁移 |
| P0-1 来源能力核对 | 用显式 JSONL 实录核对事件、身份、时间、顺序、终止和内容策略；复用公开协议 | 来源能力表、实录样本、未知字段处理；源缺少信息时明确不可用或 unknown |
| P0-2 PostgreSQL 归档 | 编写专用 schema 迁移及 ArchiveStore，按上述事务、去重、游标与快照契约实现 | 字节回放、回滚/提交响应丢失、强杀/并发/重复/截断/身份冲突测试；宿主 PostgreSQL 真实集成结果 |
| P0-3 标准与完整性 | 复用原生 OTel，补真实缺口；版本化投影和三态完整性 | 同一字节快照可重建；没有足够协议证据时保持 unknown |
| P0-4 基础流程分析 | 调用 Rust4PM，固定 case 和活动映射，输出非 LLM 变体和适用范围内的 DFG | 真实样本分析、确定输出、来源引用；缺时间/并行不伪造顺序或时长 |
| P0-5 CLI 与回归 | 注册统一 CLI 操作，增加必要配置、可选依赖、使用说明及检查范围 | 单项操作可调用；原始退出状态有效；release/download 无数据库依赖；现有 PR 检查和消费者契约不退化 |
| P0-6 同 PR 交付 | 准备四处本轮 v0.5.5 元数据，运行相关检查及现有 PR CI；人工审查合并后按既有机制正式发布 | 代码、版本、检查输入与 PR Commit 一致；正式 Release 使用真实 Run/Attempt/Manifest，未合并不发布 |
| P1 可观测性与评估 | 可选 OTLP / Collector / 一个现成后端，候选与基线比较 | 出口失败不影响原始事实；验证正确性不退化、优化比较条件明确 |
| P2 辅助与固化 | v0.5.7 先提供可追溯候选与审查依据；可选 LLM 第二输出及有明确目标后的 Pipeline / Dagger 固化后续实施 | 本轮只验收候选来源、统计、未知条件和审查边界；后续需两条输出分开、合法 Handler、可审查 diff、既有门禁有效 |

P0 是 pre-0.6.0 核心设计范围。若某项不可实现，应报告阻碍并调整交付范围，
不能把模拟测试通过当成真实采集或闭环优化成功。
各阶段验证其新增行为和受影响契约；身份匹配的已有证据继续复用，不为切换阶段重复执行检查。
不提前连写所有接口和未来空实现。

缺权限或目标归属不清时报告需要决定的事项，不自动创建新数据库或移动工作区。

已实现 `engineering-ci trace status/inspect/init/import/replay`；参数见[CLI 参考](../../guides/cli-reference.md#原始轨迹)。
`engineering-ci trace project` 使用官方 OTel SDK 生成离线 Span JSON；`engineering-ci mine` 已接入显式安装后的 Rust4PM 本地非 LLM 变体和 DFG 分析。
导入以用户给定文件为输入，回放只输出原始数据，分析以固定快照为输入。
既有 `release.py`、`download.py` 的职责不增加轨迹采集或挖掘操作。

迁移采用按版本提交的 SQL，并复用 Psycopg 事务执行；记录本组件 schema 版本和归属。
首版不增加 ORM、常驻服务或数据库任务队列，不为未经证明的吞吐需求增加连接池。
对二进制/JSON/SQL 采用成熟库和参数化接口，不自行实现它们的协议。

在功能 PR 交付前执行既有 `engineering-ci version set v0.5.5`，让版本元数据与实现一同交付。
版本准备不能留到 PR 实际合并之后，也不使身份仍匹配的既有检查证据无条件失效。

必须验证的异常还包括：来源重启及文件轮换、未知事件类型、采样/截断、迟到完成事件、
Span 父节点缺失、跨时钟偏差、解析/导出失败、不同 Attempt、运行取消和遥测队列丢弃。
明确区分原始来源已接收字节、标准化覆盖率、流程分析成功以及原任务成功。

Dagger 提供固定依赖的 Linux 分析/测试环境，Windows 验证宿主数据库连接、归档及恢复；
容器测试与宿主 PostgreSQL 集成分别记录。使用显式的测试 schema/实例，测试清理必须验证目标归属。
不把 GitHub CI 配置成访问个人宿主数据库，不将生产连接值放入日志或普通容器环境导出。
新功能要求的数据库集成测试应在现有测试调用中明确配置，缺失 fixture 不记为通过；不建立跨仓库编排。
默认回归不调用付费模型，不触发真实 GitHub Workflow，也不重新执行历史工具。
真实采集、模拟异常、离线算法分析与优化执行的证据分别记录。

## 内容策略、未完成预检与上下文衔接

已确定的选择：宿主 PostgreSQL、`VESRYN_DATABASE`、Psycopg 3、首个来源为显式桌面 Codex rollout JSONL、
成熟插桩优先、默认非 LLM 分析、原始归档与业务执行状态独立。
这些选择不因工具环境缺失而自动换成另一套后端。

仍需在对应步骤实际核对：宿主 PostgreSQL 版本及 schema 权限、当前进程的环境传递、
来源样本的可见性/时间/顺序能力、内容保留期及容量、驱动与分析后端锁定版本及跨平台兼容性。
无法核验的项明确保留未完成，不猜测账号、数据库目标、事件完整性或可用费用。

P0-0 的宿主预检、P0-1 来源适配、P0-2 归档/恢复、P0-3 OTel SDK 投影与 P0-4 历史 PM4Py 实录分析已完成分阶段验证，
实际证据与剩余限制见[阶段验收](trace-validation.md)。
运行进程读取 VESRYN_DATABASE，不在代码中添加用户注册表或第二套连接来源。
按项目上游观察规则，将遇到的 Windows free-threaded Psycopg wheel 限制记录到 `.agent/upstream-observations.md`，未开展额外上游调查。

未来扩展沿来源、投影、挖掘和执行四个边界推进；标准或后端变化不要求重新归档原始数据，
但也不承诺无需任何后续迁移。本文承担长期设计上下文，实施进度及实测结果引用各自真实 PR 和验证记录。

## 修订后的实施顺序

已完成的基础不重建。P0-1/P0-2 已在当前注册工具边界接入，验收范围与结果见
[工作流验收](workflow-validation.md)。P1 已接入下述首个受控比较入口，
其他优化指标仍为后续计划。v0.6.4 的 P2 接入下述完整 PR 检查能力的批准、启停、发现/选择
与实际反馈；实测范围以验证记录为准。

注册操作的字段补充与挖掘投影在 v0.6.3 接入：原报告提供允许公开的参数、实际工具版本、
平台/后端与统计；Runtime 提供实际调用批次。标准 XES 与 Rust4PM 共用按 Step/attempt 准入的
Event Log，跨 Step 依赖仍来自原定义，不能把共享批次的包装时间当成各项内部耗时。
具体契约见[独立生成与编排](https://github.com/dymzz/vesryn/blob/7ac74b83c4a206446b9c8b52cc88c906a13ad2f5/docs/architecture/harness/observations.md#已观测操作的-event-log-与分析)。
这补齐 P1 的可观察输入；当前进一步提供完整 PR Profile 的同输入复用比较。
P1 首个范围仅认证原报告标记的检查提交减少，保留原质量结果和复用来源；
具体准入见[受控复用比较](../architecture/harness-integration/checks.md#完整-pr-检查的受控复用比较)。
它不是安全删除检查、整体 Agent 收益或批准激活的证明；P2 用独立记录关联这份证据，
不修改 P1 的批准字段，操作与存储见[能力契约](../architecture/harness-integration/capabilities.md#能力批准版本选择与执行反馈)。

| 阶段 | 具体工作 | 准入/验收 |
| --- | --- | --- |
| P0-1：真实操作观测与证据关联 | 复用 ToolResult/检查点，补齐当前注册调用的真实身份、执行/复用和 attempt 观察；用成熟 OTel 能力做适用插桩，明确未覆盖部分 | 实际失败、复用、输入变化、中断能逐项追溯；未知信息不补造；不增加第二次 pytest 来收集观测 |
| P0-2：候选与目标的显式关联 | 首个目标继续 PR 检查复用；绑定一个实际候选、完整 Profile、独立生成文件、原执行证据和未解决条件 | 参数/环境变化使相关旧证据失效；原负向测试仍失败；观察候选、可执行目标与批准状态不会互相冒充 |
| P1：受控执行比较 | 在明确允许的试验范围执行基线/候选，保留相同代码输入、任务判据、工具环境及缓存条件；先比较真实执行/复用与检查提交次数，再考虑其他可测指标 | 原门禁不弱化、失败/恢复语义不变；收益有实际对照证据或明确 not_comparable；不把固定分析结果等价当作优化效果 |
| P2：一个目标的发现与版本选择 | 使用现有 engineering-ci CLI 作为首个调用目标，提供已批准定义与证据引用的发现/选择；再接入实际执行反馈 | 当前 Codex 能发现并调用某个已批准能力，无需重新展开其内部步骤；停用影响后续选择，不改历史或声称撤销外部副作用 |
| P3-1：反馈只读检索 | v0.6.5 按归档的批准/执行标识查询，过滤、分页、预算及内容核验 | 不重复检查/自动迁移；失败保留，稀疏页可继续；见[检索契约](../architecture/harness-integration/feedback.md#已归档能力反馈的只读检索p3-1) |
| P3-2：真实使用汇总 | v0.6.5 以显式反馈集合与 v2 Attempt 索引核验覆盖并去重，保留执行/复用及原失败 | 不直接相加累计快照；v1/缺口/冲突保持可见，统计仅限选中样本 |
| P3-3：后续审查依据 | v0.6.5 消费已验证汇总，关联原比较及明确 call 回执，提供保留、调查或新试验依据 | 原质量和记录上下文仍须可比；缺口保持可见，显式批准决定选择，不自动调优或发布 |

P1 的试验调用与 P2 的常用能力启用分开，避免“未验证不能执行、未执行又不能验证”的循环。
试验权限及边界显式给出；同一只读/检查能力在既有授权内调用不新增逐步审批。
正式 PR 合并、Release、跨仓库操作和其他副作用仍按项目/宿主的授权规则处理。

## 本轮设计审查结论

| 草稿中的冲突或过强承诺 | 本方案修正 |
| --- | --- |
| 不实现执行引擎，但要求 Workflow 固化并执行 | 复用已存在的受限 Runtime；不重建领域执行、容器或远端调度 |
| 声称核心不绑定任何 Pipeline 格式 | 核心有版本化格式，其他格式走实际适配；宿主/来源可替换 |
| 原始历史“完整”、重建“全部事件” | 只承诺已采集并提交的字节，完整性按来源协议保留三态 |
| OTel GenAI 投影自动提供操作语义 | 使用适用语义，缺失的精确身份、参数和费用保持未知 |
| Phase 3 自动参数化/能力匹配，但来源只有粗粒度活动 | 先补真实操作观测，用显式映射；证据不足的关系保持未解析 |
| 公共子序列直接变为可执行 Workflow | 优先核对完整/连续片段；数据和依赖须独立确认，不能跳过中间操作 |
| 新建通用 Candidate IR 与现有工作流定义并行 | 观察候选与现有生成/来源契约分别维护，复用同一校验与编译实现 |
| Rust4PM 全部能力均进入当前实现 | 当前复用变体/DFG；Conformance 需参考模型与实际适配/验收后再加入 |
| Schema/分析等价/一次复用即证明优化收益 | 分开记录静态、执行、门禁、效果和批准；增加受控可比证据 |
| Phase 4 同时要求 LLM、MCP、Skill、Pipeline | 首个目标为当前 Codex + CLI；其他入口按实际需求后续实现 |
| 所有反馈直接回 PostgreSQL，外部系统负责全部权限 | 存储边界显式接入；保留原权威结果，宿主与适配器仍承担真实准入 |
| 停用/回退能力版本即可回退外部任务 | 只改变后续能力选择，外部副作用按原领域规则恢复 |

P0 保留原检查及失败/恢复语义；不因新增观测改写 CI/Release 结果。
受控收益比较、批准/激活与 PostgreSQL 自动反馈未在 P0 实现。

## 实施顺序与架构验收

1. 已实现四类契约、Schema、命名和依赖方向；隔离测试核对核心不依赖项目业务。
2. 已实现每次独立生成的定义/来源及只读集中校验，配置决定工具、参数、条件和依赖。
3. 已接 checks 和报告查询适配器，保留原模块独立；实际验收记录见验证目录。
4. 已暴露五个原子检查及事实；pr 在生成时展开完整现有 Profile，同批次共享 Dagger。
5. 有实际需求后再加入 Git/GitHub/其他协议适配或独立仓库，不创建空后端。

必须有直接验收证据：

- 两次生成独立文件，生成定义、来源和结果可明确识别；旧产物不被覆盖。
- 两个不同工具的合法组合改变实际调用顺序及参数，不只是改标签；输入引用确实传递。
- 替换工具适配器不修改核心；核心隔离测试无需 engineering-ci、Dagger 或数据库。
- 丢失工具、环、类型不匹配、输出缺失、未支持能力在恰当阶段拒绝，副作用前完成可确定的校验。
- 真实测试失败、失败报告生成、同输入复用、输入变化和中断恢复保留原语义。
- 任意组合、子流程或重试不能绕过原 Release/权限/UNKNOWN 约束。
- 正向/负向实际执行与替身测试分别记录；旧绑定结果只作为历史证据，不冒充新架构验收。

Schema 主版本、工具契约版本和必需能力是兼容边界。
定义引用具体工具契约及其内容摘要，实现版本与二进制版本另入运行身份。
两个适配器可以实现同一契约；旧契约不再提供时，显式拒绝并给出迁移方式，
不能仅凭相同名字或主版本推断兼容。
新增工具或适配器通过目录扩展；未知必需能力拒绝、破坏性变化提供显式迁移，
不以不断增加业务 if/else 或修改所有已生成工作流解决版本变化。
