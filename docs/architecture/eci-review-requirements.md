# ECI 审阅要求

## 1. 入口与基线

本文件是 ECI 设计、实现、PR、复审、验收及全仓审计的直接规范入口。仓库内 Agent 由 AGENTS.md 导航；普通 Chat / GitHub Connector 不假定自动加载 AGENTS.md，应直接读取 [本文件的 main 版本](https://github.com/dymzz/engineering-ci/blob/main/docs/architecture/eci-review-requirements.md) 及 [结果 Schema](eci-review-result.schema.json)。用户只指定目标、必要范围和操作意图，不提供输入 JSON 或对象清册。

开始审阅前必须实际查询仓库 main HEAD（Git ref/branches/main），再固定规范文件所在提交、受审对象及其状态、PR HEAD、PR base 元数据、实际 merge base、净差分及本轮修订差分；需要时查实际联合候选 Merge SHA。main、PR base、merge base 和规范版本不得混同；不能用旧 checkout、PR base 或上轮会话代替当前 main。规范与受审版本分别固定，具体证据使用对应版本。无法获取时说明缺口，不声称已完成加载。已合并/关闭对象只按实际状态追溯，不作为待合并候选。

全量审阅强制执行 §2.1 的全部阶段；仅用户明确限定时缩小范围或视点。设计审阅核对目标、接口、可实施性与验收，不要求尚未实施的运行证据；实现审阅追踪实际变更及影响；验收针对当前候选、原缺陷与适用证据；全仓审计按授权范围遍历。审阅不自动授权写入、提交 Review、触发 Actions、合并或发布。

## 2. 共同方法

以工程目标、对象、关系、性质为中心，同时审阅既有工程正确性与工程演进的合理性。各视点独立发现、判断，共享事实与证据。根据需求、实际候选及适用合同，发现新增、修改、删除、替代的对象、关系、职责、合同、不变量和验证义务；比较原结构与候选结构，审阅新增结构本身及迁移影响，不限于 diff 或既有缺陷。追溯正反向依赖、入口、共享资源、动态消费者、外部接口与预期缺失关系。工程对象、技术栈、阶段、关系类型和任务编号均从实际权威发现，规则中的类型仅为非穷尽示例；未知新类型不得因此排除。使用版本控制、源码/API、配置、实际原生工具及原任务事实；候选或仅安装不算已采用。必要时超出 diff，不无据扩大到全仓。

每条规则按具体对象及性质履行，而非打勾；记录实际搜索范围、方向、版本、方法、排除及局限。仅有充分有界搜索依据才能认定无关系；静态搜索不证明动态依赖完备。发现范围未知或未完成就标 partial/unknown；不适用须有证据。严重缺陷不终止其他视点。阶段只能进一步拆分子批，不得因规模、成本、历史审阅或已发现问题而取消。

先查原 Issue、Review、缺陷及证据，再比较实际修订。保留原 Finding 身份；区分新问题、既有问题、修订核销、严重度调整，说明实际变更或新影响。不重复有效证据；仅因实际变化、矛盾、未知或明确请求补充定向验证。历史、文档一致性、安全/信任贯穿四视点。原语义关系和任务记录按[任务接续与图谱维护](agent-instructions.md#task-continuity-and-evidence-reuse)维护，机械事实从原权威派生，不复制账本。

### 2.1 强制阶段与接续

全量审阅必须经过下列阶段，不能由 Agent 判断任务复杂度后合并、省略或提前结束。明确专项仅执行用户指定视点及必要基线、对账。阶段组织审阅工作，不是 ECI 工程执行依赖；四视点各自独立发现，不以其他视点的对象清单或结论为边界。

| 阶段 | 必经工作 |
|---|---|
| A0 | 固定规范、实际基线、请求范围、初始事实及历史证据；创建接续 MD |
| A1 | Specification 独立审阅 |
| A2 | Structure 独立审阅 |
| A3 | Behavior 独立审阅 |
| A4 | Verification 独立审阅，从工程性质独立导出义务 |
| A5 | 跨中心核对遗漏、冲突、重复 Finding 与新增义务；回到受影响中心补审，再对账 |

四中心须分别实际履行并记录，不得以一次普通 Review 加分类标签代替。阶段可拆子批，共享已核实事实，复用有效证据；不因阶段编号要求重复采集或重复运行。新事实可反馈已执行中心，先核对影响再补审。

每个阶段或子批结束前必须实际更新同一审阅 MD（如 review.md，位于当前授权工作区或可下载制品），记录规范与受审版本、请求范围、阶段/子批、具体对象和关系、搜索范围、判断、证据引用、缺陷身份、未覆盖义务、阻塞及下一接续位置。A0 创建，后续保留原记录并增量更新；仅在回复中声称已记录不算完成。对应阶段 JSON 实际产物及校验记录同时保留（A0 尚无规则判断时仅记录基线，不造空 JSON）；MD 记录接续及人类可读结论，与 JSON 共用事实和缺陷引用，不另建事实账本。

收到“继续”或同义请求时，读取已有 MD 及相关 JSON，按记录从未完成阶段/子批接续；若版本变化，核对受影响义务及证据适用性，不无依据重启或核销。无法持久化/读取时明确说明阻塞及尚未完成位置，不伪造完成；资源不足保留部分结果，不能缩小请求范围。

不得以发现严重缺陷、CI 绿、既有审阅、规则数、轮次数或自判复杂度作为提前终止条件。不得自行指定“最终轮”“最后一轮”“已经足够”“无需继续”等引导用户停止的措辞。A5 是对账与补审阶段，不是预设终止轮。只报告实际覆盖、未履行义务、缺陷及证据；可以据实报告全部已请求义务的状态及工程建议，但不得自行决定停止、缩减、验收或结算，相关决定由用户作出。

## 3. 四视点规则

以下 32 个稳定规则 ID 是审阅性质分类，不是工程对象清单。每行定义关系、判断和完成条件，均适用于既有及新建/替代对象。新增性质直接在相应规则下记录 checks；发现规范未覆盖的性质时显式记录规范缺口，不丢弃发现或强套旧合同。既有生效约束仍须遵守；候选合同需独立审阅，不能仅因与旧结构不同拒绝，也不能把未经采纳的候选当成生效权威。规则数不证明完备。

### C1 Specification — 从目标、需求、裁决、设计、AC 与公共合同出发

| 规则 | 必审关系、判断及完成条件 |
|---|---|
| ECI-S01 目标与范围 | 双向追溯目标→需求→设计→实施→验收；核对新增/变更/删除目标的价值、依据、范围、遗漏、过度收缩或扩张及未交付项，逐项目标对账。 |
| ECI-S02 权威合同 | 发现现行及候选的上下游合同、约束、依赖和冲突；审阅新增合同的必要性、兼容与迁移；区分真实必要前置、并行任务、Git stack、文件交集及替代关系，不无据阻断。 |
| ECI-S03 职责与复用 | 职责→组件→公共接口→消费者；先定位同职责权威、成熟原生方案及实际复用入口。审阅新增/重组职责的内聚、边界、必要性与收益；以实际重复证据识别平行实现、转发或重造原生能力。 |
| ECI-S04 组件边界 | 发现既有与新增/替代组件的职责、权威、接口及依赖方向；核对[项目现行架构约束](../../AGENTS.md#architecture-and-ownership)与适用原合同。ECI 持有 CI/CD 工程验证、证据及交付，遵循已采用原生工具职责，禁止直接/传递依赖 Vesryn/Workflow；拟变更约束须独立审阅并经正式采纳。 |
| ECI-S05 语义与不变量 | 发现全部适用的既有、新增及修改合同与不变量，逐性质给出规范来源、适用范围、预期、冲突与缺失；审阅新合同自身的完备性、一致性及可验证性。选择不得缩小独立必需义务，诊断/原生计算不等于授权/受信复用。 |
| ECI-S06 工具与选型 | 核查原生能力、版本、限制、替代方案、实际收益；评价抽象、依赖、配置及兼容层必要性，不以防御为由延期合理设计或默认最小实现。 |
| ECI-S07 交付与验收 | 从既有和新增性质推导验收要求及方法，区分实现、接线、验证、采用、授权及收益；列独有正反例、有效证据和未证明交付，不因旧测试通过结算新性质。 |
| ECI-S08 历史与安全 | 原问题→修订/替代→现行合同；核对版本、导航、权限、Secret、信任及规范强度；保留缺陷 ID，升级/降级说明旧依据、变化及新影响。 |

### C2 Structure — 从实际源码、配置、变更对象和上下游消费者出发

| 规则 | 必审关系、判断及完成条件 |
|---|---|
| ECI-T01 变更与引用 | 从实际变更发现所有类型对象的新增、修改、删除与替代，以及定义↔调用/读取/引用/外部消费者；比较原与候选关系，记录正反向搜索、遗漏和断裂，区分真实依赖与在途 PR 文件重叠。 |
| ECI-T02 模块与职责 | 核对既有及新增组件的实际结构、依赖方向、循环、重复及转发，比较声明与实现；定位公共实现及适配必要性，区分原生工具可见边、人工语义与未观察边。 |
| ECI-T03 构建依赖 | 发现各实际构建、打包、生成、安装及运行环境的依赖闭包（声明→解析/锁定→环境→产物→消费者）；覆盖新增子工程、工具链、远端与外部消费者，核对版本、配置和更新传播。 |
| ECI-T04 Source 与 Data | 发现全部输入、来源及数据对象→选择/获取→校验→转换/物化→实际读取/消费；逐边核对身份、版本、内容、成员/路径/链接、排除及前置；区分目标物化与历史基线证明，审阅新增来源及变换合同。 |
| ECI-T05 选择与影响 | 实际变更→直接/间接、静态/动态及非代码资源消费者→受影响验证/工作义务；核对影响分析、选择与映射的实际完备性及新增机制本身。追共享配置、测试资源、插件、辅助实现等隐含消费者；记录方向、排除、遗漏和未知。 |
| ECI-T06 契约交接 | 发现新增及既有生产者→接口/数据/产物→消费者的全部相关交接；逐边核对字段、路径、命名、版本、失败/缺失、兼容、原始引用及派生消费；审阅新交接及替代/迁移关系。 |
| ECI-T07 配置与集成 | 从实际配置、规则、版本、运行环境发现适用入口及下游；检查解析、默认值、规则来源、源/消费者版本、阶段及激活条件；核对新增集成与现有配置兼容，区分配置和启用。 |
| ECI-T08 文档与关系 | 设计、代码、配置、Guide/AGENTS、Issue/PR、缺陷及现行投影对照；定位冲突、路径/Secret 出口和信任边界，历史快照不改写。 |

### C3 Behavior — 从实际入口、原生工具、事件与执行实例出发

| 规则 | 必审关系、判断及完成条件 |
|---|---|
| ECI-B01 入口 | 发现适用的既有、新增、替代及移除执行入口、事件入口、API、服务、自动化和外部消费者；逐实际入口追到行为及共享实现的反向调用，不能用一个入口证明其他入口。 |
| ECI-B02 选择与阶段 | 从真实触发与独立应履行义务追到选择、调度、执行、阶段及终止条件；核对实际范围、输入、数据前置、增量升级、跳过/不适用；审阅新阶段、分支和组合方式本身，按适用合同判断前后置条件。 |
| ECI-B03 输入与原生结果 | 逐实际执行核对参数、环境、工具版本、目标身份、物化/导出、实际收集或读取、原生输入与结果；检查新增输入/输出模式和转换是否保真；区分未启动、失败、取消、缺结果，源码推断不冒充实测。 |
| ECI-B04 身份与时序 | 发现实际执行、事件、资源、结果及新增身份类型和生命周期；核对关联键、父子、生产消费、时序、重试、并发、取消、合法多发生与冲突边界；同一版本或计划不等于同次发生，不靠最近文件/时间绑定。 |
| ECI-B05 数据结果闭环 | 执行→同次原生结果→报告/数据/产物→实际消费与裁决；核对缓存、失败/部分输出、传输/恢复及数据前置，审阅新增结果和消费机制。报告不重复计算，原生缓存非受信接纳，受信复用不切断下游产物。 |
| ECI-B06 权限失败 | 发现所有适用执行及交接边界的身份、权限、凭据、Secret、来源验证和错误传播；核对新增信任边界与失败处置，诊断/格式通过不授予必需判定或发布权，不误拒合法消费者和独立执行。 |
| ECI-B07 实际采用 | 从既有及新工具/规则/能力→配置→真实调用→执行→证据；区分登记、安装、实现、配置、接线、启用及验收；核对默认、显式及增量等实际采用范围，不以无关性能前置阻断。 |
| ECI-B08 资源成本 | 从实际资源及控制/数据路径发现计算、I/O、进程/并发、传输、外部调用、缓存与重复工作；审阅新增机制成本，墙钟、累计、阶段、并行分开；收益须可比实测且不损义务，测量接线不冒充优化。 |

### C4 Verification — 从应证明性质、Check/AC、测试及原始证据出发

| 规则 | 必审关系、判断及完成条件 |
|---|---|
| ECI-V01 义务覆盖 | 独立从既有及新增目标、合同、不变量与风险导出验证义务，双向对账性质↔测试/检查/AC↔实际验证；查独有正反例、失败/边界及未证明性质，旧测试数/全绿/格式不代替新性质验证。 |
| ECI-V02 测试收集 | 从各实际验证体系发现验证用例、共享资源、配置、参数、替身与断言→被测性质；核对发现/收集、选择、执行、跳过、setup/teardown、多实例、并发、隔离及映射，查漏测和重复低价值验证，保留独有证明。 |
| ECI-V03 原生真实性 | 按实际入口、输入、配置、版本、环境、范围→原生退出及结果验证真实行为；适用于新增验证方法及执行体系；替身不能冒充真实原生执行，按变化与风险定向验证。 |
| ECI-V04 证据适用 | 证据→所支持/反驳命题；发现真实候选、执行身份、产物、来源/时间/范围及新增证据类型，核对实际适用性；区分直接读取、原生实测、复用、推断、未知与反证。 |
| ECI-V05 接纳与 Required | 核对适用及新增证据接纳、来源/资格、输入、规则、实际执行、覆盖、独立必需集合及裁决/授权条件；选择、缓存、遥测、Schema PASS、原生成功不等于受信接纳，按实际场景核对后置阶段。 |
| ECI-V06 报告交付 | 原始结果/报告/证据产物→实际消费及裁决；核对既有及新交付机制的同次退出、完整/中断/缺失/封存失败、合法多执行及覆盖，不重复扫描或以诊断替代退出。 |
| ECI-V07 历史复验 | 原 Finding→修订→实际差分→原适用证据/必要新证据→结算；保留身份，核销不重开，重复探针或严重度修订说明变化/矛盾/独有价值。 |
| ECI-V08 验收风险 | 当前候选、适用验证、AC、真实阻断、非阻断交接及未知边界；独立核对新增性质与迁移风险，区分覆盖、性质、工程验收和有权动作；成本证据可比，现有 CI 绿不掩盖逻辑错误。 |

## 4. 权威关系导航

按实际影响发现关系链，例如目标→需求→实施→验收，输入/来源→选择/变换→实际消费→结果，前置/生产者→数据/接口→消费者，执行→证据→接纳/裁决→交付，能力→配置→采用→效果，缺陷→修订→影响→复验，公共合同→跨仓消费。上述是关系模式而非固定流水线或穷举；新增、替代、删除关系同样审阅，不另建图谱。

从[项目职责](../../AGENTS.md#architecture-and-ownership)、[仓库介绍](repository-overview.md)、[架构索引](README.md)、[任务接续](agent-instructions.md)、[验证入口](../../guides/common-tasks.md)、[设计索引](../../design/README.md)、[验证记录](../verification/README.md)及实际相关 Issue/PR 发现适用权威，再沿原合同和实际消费者扩展。导航只提供起点，不是固定任务列表或审阅边界；区分生效、候选、历史与实际实现，不将设计或工具登记当成已采用事实。

## 5. 输出与校验

### 5.1 实际输出

读取并使用 [eci-review-result.schema.json](eci-review-result.schema.json)（Draft 2020-12，2.0）。生成实际 review-result.json，再由同一记录给出人类可读 Review；不要仅在 Markdown 末尾附四中心概括。各中心按规则记录 coverage、discovery、scope、method、limitations、evidence_refs 和具体 checks（对象引用、性质、判断、证据/缺陷引用）。引用原事实，不复制图谱。Finding 含预期、实际、影响、原主责、可复用实现与修订、验收及历史依据；复用证据须说明适用性，违反须引用开放 Finding。

每个中心阶段/子批交付 partial_batch，requested_viewpoints 始终保留实际完整请求（全量为四中心），centers 仅填本批实际审阅的规则；不得把单中心批次冒充用户专项或整体 accept。complete_request 仅用于跨中心实际汇聚，须覆盖请求中心全部规则 ID（含未知/未审及有据不适用）；不代表实际完成或通过。汇聚按同基线、规范摘要、规则、对象、性质对账，共享证据和原 Finding 身份，缺失/冲突回对应中心补审；保存阶段 MD、各批 JSON 及汇聚校验记录。未发现范围不能凭自报证明完整。

### 5.2 实际校验

由执行者从实际请求和 Git/GitHub 获取 subject、head、base（受审比较基线，区别于当前 main）、task-kind、视点；从实际读取文件计算 requirements/schema SHA-256，不从结果反推校验参数。使用同一规范版本的 [validate.py](../verification/review-experiment/validate.py) 和原生 jsonschema：

```bash
uv run --script docs/verification/review-experiment/validate.py review-result.json \
  --subject "$SUBJECT" --head "$HEAD_SHA" --base "$BASE_SHA" \
  --task-kind implementation
```

非 PR 可省略 --base；明确专项才传 --viewpoints；任务类型按实际请求。Chat 无 checkout 时，可通过连接器读取固定提交的 MD、Schema、脚本到执行环境，保持上述相对路径，用可用 Python/jsonschema 实际执行同一校验，不要求另建工作树或用户上传。缺文件、工具或执行能力时如实说明，不伪造校验结果。

交付时报告规范提交、main、PR base/merge base/HEAD（适用时）、实际 JSON 文件及校验退出/结果、四视点覆盖和未知；校验未执行或失败，不称为合规审阅，保留有价值的部分诊断。退出 0 仅证明结构、请求/基线/摘要绑定、局部引用及声明覆盖一致性，不证明真实发现完备、证据真实性、工程性质或授权。

试验消费者不改变 ECI 依赖/锁、Hook、CI 或发布门禁。通用规范与验证由 Knowledge 持有，正式公共资产采用后迁移；宿主自动加载、原生结构化生成及独立事实覆盖仍需验收。实施验收和历史试验见[审阅试验记录](../verification/review-experiment/README.md)。
